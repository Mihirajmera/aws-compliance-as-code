# Learnings

## Day 01

Four words that get used interchangeably are actually four different layers, and IAM-01 (root account MFA) shows all of them. The **requirement** is what a framework says in its own language: NIST IA-2(1) says privileged accounts must use multi-factor authentication, and ISO A.8.5 asks for secure authentication. The **control** is how we meet that requirement in our environment: "the AWS root user must have MFA enabled." The **test** is the repeatable procedure that proves the control is working, which here is calling `iam:GetAccountSummary` and checking that `AccountMFAEnabled` equals 1. The **evidence** is the output of that test, the saved JSON response with a timestamp and account ID, which an auditor can inspect without ever logging into the console.

The crosswalk matters because auditors and compliance teams rarely deal with only one framework. Without a crosswalk, the same root-MFA setting gets tested and screenshotted separately for SOC 2 CC6.1, ISO A.8.5, NIST IA-2(1) and CIS 1.5, which wastes time and produces four slightly different answers to one question. With a crosswalk, the team tests once and reuses one piece of evidence for every framework it maps to. It also shows gaps quickly: if a framework requirement has no control mapped to it, that is a hole the team needs to fill before the auditor finds it. Finally, it gives everyone a shared vocabulary, so an engineer who thinks in AWS settings and an auditor who thinks in control IDs can point at the same row and agree on what is being proven.

## Day 02

My access-key-age check (IAM-04) starts by calling `iam:ListUsers` through a paginator, so it still works when there are more users than fit in one API page. For each user it calls `iam:ListAccessKeys`, which returns every key with its `Status` and `CreateDate`. The check subtracts `CreateDate` from the current UTC time to get each key's age in days, and any key that is both `Active` and older than 90 days becomes a finding. If there are no findings the status is PASS, otherwise FAIL, and the result also carries the API call names and the raw key metadata, so an auditor can re-perform the test from the evidence without trusting my code. Inactive keys are skipped on purpose, because a disabled key cannot be used even if it is old.

I test it with moto because moto fakes the IAM API in memory, so the tests never touch a real account, cost nothing, need no credentials and run the same way on any laptop or in CI. That lets me build exact situations that are hard to set up for real, such as a user with an active key, the same key after it is deactivated, or no password policy at all. The awkward part is that moto stamps new keys with today's date, so to test the FAIL path the check takes an optional `now` argument and the test pretends it is 91 days later. The tests prove the PASS/FAIL logic is right, and the run against the sandbox proves the API calls and permissions are right; together they give me confidence in the evidence.

## Day 03

Every evidence file stores the raw API response next to a SHA-256 hash of that response. Before hashing, the raw data is turned into canonical JSON: keys sorted, no spaces, and datetimes converted to strings, so the same data always produces exactly the same bytes and therefore the same hash. To check a file, anyone can reload `raw`, serialize it the same way and recompute the hash. If someone later changes even one character, for example flipping `"AccountMFAEnabled": 0` to `1` to turn a FAIL into a PASS, the recomputed hash no longer matches the stored `sha256`, so the edit is exposed. SHA-256 is designed so that finding different data with the same hash is not practical.

The weakness is that the hash sits in the same file as the data it protects, and nothing protects the hash itself. Anyone who can edit `raw` can also recompute the hash and overwrite `sha256`, and the file will verify perfectly. So the hash proves the file is internally consistent, not that it is the original. To close that gap the hash has to live somewhere the editor cannot reach: signed with a key the editor doesn't hold, written to an append-only or write-once store such as S3 Object Lock, or chained so each file includes the previous file's hash. CloudTrail log file validation solves exactly this problem for AWS logs, because AWS signs a digest of the log hashes every hour with its own private key, which is why turning it on (LOG-02) is a control over evidence integrity and not just a logging setting.

## Day 04

OSCAL breaks compliance into layers: a catalog lists controls (the NIST 800-53 catalog), a profile picks a baseline from it, a component definition or SSP says how a system implements each control, an assessment plan says how they will be tested, assessment results record what the testing found, and a POA&M tracks fixing what failed. My project produces the assessment-results layer. Each evidence file becomes an observation, which is the raw thing I collected, with a link to the file and its SHA-256. Each observation is then tied to one or more findings, which say whether a specific NIST control objective, such as `ia-2.1_obj` for root MFA, is satisfied or not. My `import-ap` is just a placeholder because I have not written a formal assessment plan, and the failed findings would be the natural input to a POA&M later.

OIDC is better than storing AWS keys in GitHub secrets because there is nothing long-lived to steal. With secrets, an access key sits in GitHub forever, works from anywhere, and has to be rotated by hand, which is exactly what my own IAM-04 check would flag. With OIDC, each workflow run asks GitHub for a signed token, and AWS swaps it for credentials that expire within an hour. The role's trust policy only accepts tokens whose subject is `repo:Mihirajmera/aws-compliance-as-code:ref:refs/heads/main`, so a fork, another branch or another repo cannot assume it. The role only has SecurityAudit, so even a stolen session could read configuration but not change anything.
